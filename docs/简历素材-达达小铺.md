# 达达小铺（本地生活点评平台）· 后端开发

> 简历素材。写进简历时按需删减；**面试问答准备**见文末。

## 项目简介

基于 Spring Boot 的本地生活点评类后端服务，覆盖商户浏览、探店笔记、关注 Feed、优惠券秒杀等核心场景。项目重点解决**高并发秒杀下的超卖与重复下单**，以及**热点数据的缓存穿透/击穿**问题，并围绕消息投递可靠性做了一套完整的工程化处理。

## 技术栈

- **框架**：Java 8、Spring Boot 2.3.12、MyBatis-Plus 3.4.3
- **存储/中间件**：MySQL、Redis（Lettuce）、RabbitMQ（spring-amqp）、Redisson
- **鉴权/工具**：JWT（Hutool）、Knife4j / Swagger
- **部署**：Nginx 独立承载前端与静态资源，后端仅提供 JSON API

## 个人职责

- 负责**秒杀模块**的整体设计与实现：Redis + Lua 原子扣减、RabbitMQ 异步落库、延迟队列超时取消、失败补偿与人工兜底
- 负责**缓存层**设计：抽象通用缓存模板，解决穿透/击穿，保证缓存与数据库一致
- 负责**认证体系**：JWT 无状态鉴权、拦截器统一校验、ThreadLocal 用户上下文
- 负责**消息链路可靠性**：发布确认、手动 ACK、死信分流、幂等设计与崩溃恢复

## 技术亮点

### 一、秒杀：从「抗住并发」到「不丢一单」

**1）Lua 原子化，热路径完全不碰数据库**

把「校验库存 → 一人一单 → 扣减库存 → 记录已购 → 消息入队」五步合并进**一条 Lua 脚本**。下单接口全程只有**一次 Redis 往返**，既不查库也不发 MQ，把数据库从热点路径上彻底摘掉。

> 关键取舍：消息入队也放进 Lua，是为了消除「库存扣了但消息没记下」的窗口 —— 两者在同一个原子单元里，要么都成功要么都失败，因此**不需要任何补偿逻辑**。

**2）RabbitMQ 异步落库 + 可靠投递 + 崩溃自愈**

接口在 Redis 内闭环后立即返回订单号，真正建单由消费者异步完成。生产者侧用 `BRPOPLPUSH` 实现可靠投递：消息先转入 `processing` 队列，**等 broker 确认后才删除**；进程崩溃时消息仍留在 `processing`，应用启动时把该队列整体搬回待投递队列。（实测 `kill -9` 应用后重启，卡在投递中的订单仍成功落库。）

> 判断：relay 跑在独立线程、不在请求线程上，所以可以放心用**同步等确认**，替代异步回调 + 在途消息表，逻辑显著简化。

**3）三层幂等防线**

| 层 | 机制 | 挡住什么 |
|---|---|---|
| Redis | Lua 里 `SISMEMBER` | 用户重复点击（**快筛**） |
| DB | 主键 `id` | 同一条消息被重复投递 |
| DB | `uk_user_voucher` 唯一索引 | 一人一单的**权威**保证 |

Lua 是快筛而非事实源——Redis 丢数据、绕过脚本的路径都可能漏，真正兜底的是唯一索引。据此对两种 `DuplicateKeyException` 做了**相反处理**：撞主键＝同消息重投（Redis 只扣过一次，绝**不**回滚）；撞唯一索引＝库存被多扣（**必须**补回并恢复「已购」标记）。

**4）手动 ACK + 两级死信**

- **手动 ACK**：处理成功才确认，避免消费中途进程挂掉丢消息
- **两组独立死信**：建单失败（要告警、要人工）与超时取消（正常流程）分开，语义不混
- **踩坑记录**：`acknowledge-mode: manual` 下**容器不会替你 nack** —— 重试耗尽后消息不被拒绝，而是一直 unacked、channel 关闭时重回队列、无限重投（实测扣库存 SQL 空跑 5 次）。最终改为**显式重试 + 显式 `basicNack(requeue=false)`**
- **失败兜底**：落失败表 + 告警 → 定时任务重试 3 次 → 转「待人工审核」，避免对坏消息无限重投

**5）延迟队列实现 15 分钟未支付自动取消**

死信 + 队列级 TTL：消息先进无消费者的延迟队列，到期死信到取消队列，消费者取消未支付订单并回滚双端库存。取消是**带状态条件的乐观更新**，重复收到消息影响行数为 0，天然幂等。

### 二、缓存：穿透、击穿与一致性

**1）把缓存策略抽象成可复用模板**

手写泛型缓存模板 `RedisClient`，业务侧一行调用：

| 方法 | 解决的问题 |
|---|---|
| `queryWithPassThrough` | **穿透**：未命中查库，不存在则写空值哨兵 + 短 TTL，防恶意 ID 反复打库 |
| `queryWithPathThroughAndLogicExpire` | **击穿**：逻辑过期 + 互斥锁 + 异步重建，热点 key 失效瞬间不会同时打库 |

**2）逻辑过期方案**

缓存不设物理 TTL，过期时间包在 value 里（`RedisData{expireTime, data}`）。命中后判断逻辑过期：未过期直接返回；已过期则抢互斥锁、丢线程池**异步重建**，当前请求返回旧数据。热点 key 永不「同时失效」，也不阻塞请求。

**3）一致性：Cache-Aside**

更新走**先更新数据库、再删除缓存**，而非更新缓存，避免并发写脏数据。

**4）其余缓存实践**

分类整表用 **List** 缓存 · 附近商户用 **GEO** 按距离排序分页 · 点赞用 **ZSet**（score 存时间戳，天然支持「最新点赞」）· 关注 Feed 用**推模式**写入粉丝收件箱 + `ZREVRANGEBYSCORE` 滚动分页 · 签到用 **Bitmap**，位运算统计连续天数

## 简历一行版（浓缩）

> 主导秒杀模块重构：将下单热路径收敛为「一条 Lua 脚本 + 一次 Redis 往返」，全程不触数据库；基于 RabbitMQ 与可靠队列模式（BRPOPLPUSH + 确认后删除 + 启动补偿）实现异步落库与崩溃自愈；配合 `(user_id, voucher_id)` 唯一索引与两级死信，保证不超卖、不重复下单、不丢单。

## 面试问答准备

这几问基本必然被问到，答案都在上面的亮点里、也都在代码里：

1. **为什么消息入队要放进 Lua，而不是 Lua 之后再写一张本地消息表？**
   两段式（Lua 扣库存 → INSERT 消息表）中间有窗口，JVM 崩在那里就是「库存扣了、消息没了」；补偿回滚本身也会失败。放进同一条 Lua 后窗口消失，不需要补偿。

2. **`BRPOPLPUSH` 和 `BRPOP` 差在哪？为什么不能用后者？**
   `BRPOP` 取走即删除，取走后、MQ 确认前崩溃消息就真没了（而库存已扣）。`BRPOPLPUSH` 先把消息挪到 `processing`，确认成功才删除，崩溃时消息还在。

3. **手动 ACK 下，重试耗尽的消息怎么进死信？**
   关键坑：手动 ACK 模式下**容器不会替你 nack**，Spring Retry 重试耗尽抛出的异常不会触发容器拒绝 → 消息一直 unacked → 无限重投。必须由消费者**显式重试 + 显式 basicNack(requeue=false)**。

4. **唯一索引和 Lua 的 `SISMEMBER` 各挡什么？为什么两个都要？**
   `SISMEMBER` 挡正常重复点击，但在 Redis 上、不是事实源，Redis 丢数据就失效；唯一索引是数据库层原子保证的权威约束。两者是「快筛 + 兜底」的关系。

5. **订单取消后，为什么这个用户不能再抢同一张券？**
   取消时订单行还在表里，`uk_user_voucher` 索引位仍被占用，DB 不可能再接受同一 `(user, voucher)`。所以 Redis 侧的「已购 Set」也必须保留该用户，否则会出现「Redis 放行、DB 必然拒绝」的两边打架。

6. **`seckill.lua` 里库存判空为什么不能省？**
   `tonumber(redis.call('get', key))` 在 key 不存在时得到 `nil`，`nil <= 0` 会让**整个脚本**报错 → 接口 500 而不是「库存不足」。必须先判 nil。
